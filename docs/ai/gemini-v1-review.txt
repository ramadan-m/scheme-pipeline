## 1. Critical & High-Priority Issues

### 1.1 Startup Crash on Database Boot Race Condition
* **File:** [Program.cs](file:///C:/Projects/scheme-pipeline-v1-review/api/SchemePipeline.Api/Program.cs#L27-L45)
* **Issue:** 
  In [Program.cs:27](file:///C:/Projects/scheme-pipeline-v1-review/api/SchemePipeline.Api/Program.cs#L27):
  ```csharp
  await app.Services.GetRequiredService<SchemeStore>().EnsureIndexesAsync();
  app.MapSchemeEndpoints();
  app.MapGet("/health", ...);
  app.Run();
  ```
  `EnsureIndexesAsync()` is awaited **before** `app.Run()`. If MongoDB is slow to boot (or down), index creation blocks for the driver's default 30-second server selection timeout and throws an unhandled exception, terminating the API process. Because `app.Run()` is never reached, the `/health` endpoint never starts listening. The `/health` route was given a 2-second timeout specifically to report 503 quickly, but it cannot function if the process crashes during startup.
* **Impact:** [start.bat](file:///C:/Projects/scheme-pipeline-v1-review/start.bat#L13-L25) starts MongoDB and immediately spawns `dotnet run`. If Mongo takes 2–3 seconds to initialize sockets, the API crashes.
* **Recommendation:** Move index initialization into an `IHostedService` / `BackgroundService`, or initialize indexes lazily/resiliently on readiness check.

---

### 1.2 Unpaginated Full-Collection Scans & Memory Pressure (DoS Risk)
* **Files:** [SchemeEndpoints.cs](file:///C:/Projects/scheme-pipeline-v1-review/api/SchemePipeline.Api/Http/SchemeEndpoints.cs#L39-L41), [SchemeEndpoints.cs](file:///C:/Projects/scheme-pipeline-v1-review/api/SchemePipeline.Api/Http/SchemeEndpoints.cs#L68-L69), [SchemeStore.cs](file:///C:/Projects/scheme-pipeline-v1-review/api/SchemePipeline.Api/Data/SchemeStore.cs#L34-L40)
* **Issue:** 
  1. `GET /api/schemes`: [store.ListAsync(statusFilter, ct)](file:///C:/Projects/scheme-pipeline-v1-review/api/SchemePipeline.Api/Data/SchemeStore.cs#L34) performs an unpaginated query returning **every** document matching the status filter. Sorting is then executed **entirely in memory** via LINQ ([`SchemeSorting.Sort`](file:///C:/Projects/scheme-pipeline-v1-review/api/SchemePipeline.Api/Domain/SchemeSorting.cs#L7)), which computes totals per scheme during sorting and again when mapping responses.
  2. `GET /api/summary`: Pulls all scheme records across the entire database over the network to compute portfolio totals in memory in C# rather than leveraging a MongoDB aggregation pipeline (`$unwind` / `$group`).
* **Impact:** As the portfolio grows, this leads to large memory allocations, garbage collection pauses, and potential API starvation / denial-of-service.
* **Recommendation:** Introduce pagination parameters (`page`, `pageSize` or cursor-based) on `GET /api/schemes`. Push sorting and summary aggregation down to MongoDB:
  ```csharp
  // For summary: use MongoDB aggregate pipeline
  var summary = await _schemes.Aggregate()
      .Unwind<Scheme, UnwoundScheme>(s => s.Tenures)
      ...
  ```

### 1.3 Missing Concurrency Control on Scheme Updates (Data Overwrite Risk)
* **File:** [SchemeStore.cs](file:///C:/Projects/scheme-pipeline-v1-review/api/SchemePipeline.Api/Data/SchemeStore.cs#L54-L64)
* **Issue:** 
  In [`UpdateAsync`](file:///C:/Projects/scheme-pipeline-v1-review/api/SchemePipeline.Api/Data/SchemeStore.cs#L54):
  ```csharp
  public async Task<Scheme?> UpdateAsync(Guid id, Scheme changes, CancellationToken ct = default)
  {
      var update = Builders<Scheme>.Update
          .Set(s => s.Name, changes.Name)
          .Set(s => s.SiteAddress, changes.SiteAddress)
          .Set(s => s.Status, changes.Status)
          .Set(s => s.Tenures, changes.Tenures)
          .Set(s => s.UpdatedAt, Now());
      ...
      return await _schemes.FindOneAndUpdateAsync<Scheme>(s => s.Id == id, update, options, ct);
  }
  ```
  There is no optimistic locking (e.g., checking `UpdatedAt == expectedUpdatedAt`, or an `ETag` / `version` field). If User A and User B open the same scheme simultaneously, the last write silently overwrites the previous edits with no conflict detection.
* **Recommendation:** Include `If-Match` / `concurrencyToken` (or pass `UpdatedAt` in the filter `s => s.Id == id && s.UpdatedAt == expectedUpdatedAt`) and return `409 Conflict` if the document was modified by another user.

### 2.2 Inefficient Re-fetching & Coupled Failure in `App.tsx`
* **File:** [App.tsx](file:///C:/Projects/scheme-pipeline-v1-review/web/src/App.tsx#L19-L32)
* **Issue:**
  In `App.tsx`:
  ```tsx
  useEffect(() => {
    const controller = new AbortController()
    Promise.all([api.list(status, sort.key, sort.desc, controller.signal), api.summary(controller.signal)])
      .then(([list, summary]) => { ... })
      .catch(() => { ... })
    return () => controller.abort()
  }, [status, sort, reloads])
  ```
  1. The portfolio summary is independent of table sorting and status filtering, yet every time a user clicks a table header to sort or changes the status filter, `api.summary()` is re-requested from the server.
  2. Because of `Promise.all`, if `api.summary` fails or times out, the table also crashes with `"Couldn't load schemes."` even if `api.list` succeeded.
* **Fix:** Split summary loading into its own `useEffect` (triggered on mount and `reloads`), or use `Promise.allSettled`.

### 2.3 Form Input Edge Case with `Infinity` & Misleading Error Message
* **Files:** [SchemeForm.tsx](file:///C:/Projects/scheme-pipeline-v1-review/web/src/SchemeForm.tsx#L38-L54), [api.ts](file:///C:/Projects/scheme-pipeline-v1-review/web/src/api.ts#L65-L76)
* **Issue:**
  In `readNumber`:
  ```ts
  function readNumber(text: string) {
    const cleaned = text.replaceAll(',', '').trim()
    return cleaned === '' ? null : Number(cleaned)
  }
  ```
  If a user inputs `"Infinity"`, `Number("Infinity")` returns `Infinity`. Because `Number.isNaN(Infinity)` is **`false`**, `unreadableNumbers` does not flag it.
  When serialized via `JSON.stringify`, `Infinity` becomes `null` (`{"homes": null}`).
  The API's `TenureLineRequest` expects a non-nullable `decimal Homes`. ASP.NET Core fails JSON binding with a `BadHttpRequestException`.
  Because `BadHttpRequestException` does not return a RFC `ValidationProblem` body with field errors, `api.ts` cannot parse a validation error and throws a generic HTTP 400 error. The form displays:
  > *"Couldn't save the scheme. Check the API is running, then try again."*
* **Fix:** Use `Number.isFinite(n)` instead of `!Number.isNaN(n)` in `unreadableNumbers`.

### 2.4 Lack of Focus Trap & Focus Restoration in Side Panel Drawer
* **File:** [SchemeForm.tsx](file:///C:/Projects/scheme-pipeline-v1-review/web/src/SchemeForm.tsx#L108-L121)
* **Issue:**
  1. **Focus Trap:** When the panel opens, `autoFocus` focuses the Name input, but a keyboard/screen-reader user can Tab straight out of the drawer into the underlying table and header.
  2. **Focus Return:** When the form is cancelled or saved (`setEditing(null)`), focus is lost and resets to `document.body`, forcing keyboard navigation to start over from the top of the page.
  3. **Escape Key Handling:** `onKeyDown={(e) => e.key === 'Escape' && onCancel()}` is placed on `<aside>`. If focus moves outside the drawer, Escape no longer closes the panel.
* **Fix:** Implement standard modal/dialog semantics (`role="dialog"`, `aria-modal="true"`), trap focus within the panel, listen for Escape on `window`, and restore focus to the triggering element upon dismissal.

### 2.6 Missing Currency Scale/Precision Check
* **File:** [SchemeValidator.cs](file:///C:/Projects/scheme-pipeline-v1-review/api/SchemePipeline.Api/Http/SchemeValidator.cs#L45-L46)
