### Verdict

This is an exceptionally disciplined, high-calibre take-home project: the domain maths are rigorously tested with explicit financial rounding rules (`MidpointRounding.AwayFromZero`), the C# Minimal API and React front end communicate via well-aligned contracts guarded by Zod, and security fundamentals for a localhost tool (typed MongoDB builders, mass-assignment guards, strict JSON deserialization) are solid. The main defects are a UI copy inconsistency in the portfolio summary when schemes are unvalued, an unhandled HTTP 500 when an API request body is `null`, an omitted `DELETE` capability that was part of the original problem statement, and a false sense of security in the 500 error test caused by `WebApplicationFactory` defaulting to Production.

### Design Challenges (Section 6)

| # | Choice | Why you'd do it differently | Trade-off you accept |
|---|---|---|---|
| 1 | In-memory sorting and portfolio aggregation ([SchemeEndpoints.cs:40,69](file:///C:/Projects/scheme-pipeline/api/SchemePipeline.Api/Http/SchemeEndpoints.cs#L40)) | Computing totals exclusively in C# requires `ListAsync` and `Summary` to pull all matching (or all) documents across the wire into web server memory. As the collection grows, sorting by Homes or Value evaluates `SchemeMaths.For` repeatedly during `OrderBy`, and `Summary` becomes an $O(N)$ memory transfer. Storing denormalized totals on the document or using a MongoDB aggregation pipeline (`$unwind`, `$group`) would delegate sorting and aggregation to the database. | Calculating on read avoids schema denormalization, transaction/concurrency synchronization, and complex Mongo aggregation queries, keeping `SchemeMaths` as the single pure source of mathematical truth for small datasets. |
| 2 | Non-nullable `decimal Value` in `Totals` ([SchemeMaths.cs:3,12](file:///C:/Projects/scheme-pipeline/api/SchemePipeline.Api/Domain/SchemeMaths.cs#L3)) | `Totals.Value` defaults to `0m` when all homes are unvalued. This conflates a scheme with zero financial value (e.g. 0 homes) with a 100-home appraisal scheme awaiting initial valuation. In `SchemeSorting.cs:13`, unvalued schemes sort alongside £0 schemes. The front end is forced to reconstruct whether homes are valued by checking `totals.unvaluedHomes === totals.homes`. Making `Value` nullable (`decimal?`) when `unvaluedHomes === homes` would represent the domain state explicitly. | Keeping `Value` as a non-nullable `decimal` simplifies arithmetic sums across schemes without nullable propagation. |
| 3 | Unbounded index creation blocking API startup ([Program.cs:27](file:///C:/Projects/scheme-pipeline/api/SchemePipeline.Api/Program.cs#L27)) | Calling `await store.EnsureIndexesAsync()` directly in the startup path without a cancellation timeout means that if MongoDB is down when the API launches, the host blocks for the driver's default 30-second server selection timeout and crashes before `app.Run()`. The web server never binds port 5080, preventing `/health` from ever serving the 503 response designed for it. Wrapping index creation in a resilient background task or passing a short timeout allows the server to boot and report health accurately. | Startup index verification guarantees that no HTTP requests hit the database before required indexes are guaranteed to exist. |

### What Was Checked and Found to Be Clean

- **Arithmetic & precision:** Decimal arithmetic is preserved end-to-end; `MidpointRounding.AwayFromZero` is verified for financial rounding; pence are retained in totals without floating-point drift.
- **Pipeline sorting:** Status enum pipeline ordering (`Appraisal -> Planning -> OnSite -> Complete`) is stable and correctly tie-broken by Name ascending even under descending status sorts.
- **Over-posting & mass assignment:** Contracts strictly separate input (`SchemeRequest`) from persistence (`Scheme`). Client-supplied IDs, creation dates, or extra JSON fields cannot override server-generated version 7 Guids or timestamps.
- **MongoDB query safety:** All queries use strongly-typed builders (`Builders<Scheme>.Filter.Eq`, LINQ expressions); no raw BSON string interpolation exists.
- **Concurrency & timestamps:** MongoDB updates use atomic `$set` with `FindOneAndUpdate` and `ReturnDocument.After`, ensuring `CreatedAt` remains untouched while `UpdatedAt` advances monotonically.
- **Input boundary sanitization:** Input values undergo strict verification (name/address length limits, integer home checks using `decimal.Truncate`, bounds up to 100,000 homes / £100m value, and duplicate tenure line detection).
- **Accessibility & mobile UX:** WAI-ARIA tables use proper `aria-sort`, forms use `aria-invalid` linked to error messages via `aria-describedby`, screen-reader announcements on `<TenureBar>` are clean, and responsive CSS properly toggles the inline tenure bar without double-reading.
